## New actionable defects

### NEW-330 · P0 · Stripe webhook can mark unrelated invoices PAID
- **Location:** `src/modules/payments/webhooks.ts:218-245`
- **Proof:** `invoice.paid` executes `UPDATE invoices SET status = 'PAID' WHERE account_id = ? AND status = 'ISSUED'` instead of matching exactly one Stripe invoice.
- **Impact:** One successful Stripe payment can falsely settle other issued invoices of the same customer.
- **Fix:** Persist Stripe invoice ↔ Fortless invoice mapping, verify amount/currency and enforce single-invoice idempotent settlement.
- **Accept:** Account with three issued invoices: one matching Stripe invoice.paid changes exactly one invoice; duplicates do nothing.

### NEW-331 · P0 · TECH_ADMIN can grant OWNER role
- **Location:** `src/modules/identity/teams.ts:69-123`, `src/server.ts:1020-1043`
- **Proof:** TECH_ADMIN is authorized as inviter, but requested `role: OWNER` is accepted without role-grant ceilings.
- **Fix:** Only OWNER may grant/invite OWNER; recent MFA step-up for ownership changes; enforce in backend.
- **Accept:** TECH_ADMIN invitation to OWNER rejected; existing OWNER may invite with current step-up.

### NEW-332 · P0 · Production cPanel/VPS routing uses mocks
- **Location:** `src/modules/outbox/worker.ts:19-34`, `src/index.ts:44-93`
- **Proof:** `getAdapterForService()` instantiates `MockCpanelAdapter` / `MockProxmoxAdapter`. Bootstrap only configures real Pterodactyl.
- **Fix:** Configured per-provider registry for real WHM/Proxmox adapters, fail closed when missing, disallow test mocks in live mode.
- **Accept:** Production route never returns a Mock*Adapter; remote resource actually exists on provider after provisioning.

### NEW-333 · P0 · Local subscription cancellation is not propagated to Stripe
- **Location:** `src/modules/billing/subscriptions.ts:56-132`
- **Proof:** SQLite state and auto_renew change, but no Stripe subscription API cancellation/update.
- **Impact:** Hosted service can look canceled while Stripe keeps renewing charges.
- **Fix:** Idempotent Stripe cancellation/cancel_at_period_end followed by durable reconciliation, distinct pending state and retries.
- **Accept:** Immediate and end-of-cycle cancel reflected in both Stripe test mode and Fortless after network errors.

### NEW-334 · P0 · Staff refund is local-only
- **Location:** `src/modules/payments/webhooks.ts:521-577`, `src/server.ts:1920-1950`
- **Proof:** `processStaffRefund` decreases amount paid and updates local status, but never calls Stripe Refunds API; full refund updates service locally without termination outbox.
- **Fix:** Create idempotent PSP refund and track PSP refund ID/status; only finalize ledger on confirmed provider event; issue service lifecycle job if policy requires.
- **Accept:** Refund action creates exactly one Stripe refund with matching amount; forced PSP failures leave ledger reconcilable.

### NEW-335 · P1 · Cumulative partial refunds double-subtracted
- **Location:** `src/modules/payments/webhooks.ts:105-145`
- **Proof:** Each `charge.refunded` event subtracts `charge.amount_refunded`, which is cumulative across partial refunds, rather than refund delta.
- **Fix:** Match unique refund IDs and apply only new delta, or store last cumulative amount and apply its positive difference.
- **Accept:** €2 then €3 partial refund from €10 charge leaves €5 paid, not €3.

### NEW-336 · P1 · Paid Stripe renewal does not unsuspend provider
- **Location:** `src/modules/payments/webhooks.ts:218-246`
- **Proof:** `invoice.paid` marks subscription ACTIVE but does not enqueue/reactivate a service suspended by dunning.
- **Fix:** Match invoice, confirm renewal payment, enqueue idempotent unsuspend for billing-suspended service.
- **Accept:** Payment retry after grace-period suspend restores access once.

### NEW-337 · P1 · Outbox dead-letter overwrites contract state irrespective of event
- **Location:** `src/modules/outbox/worker.ts:145-183`
- **Proof:** On any DEAD_LETTER, unconditional `UPDATE services SET contract_status='SUSPENDED'` and `service.provision_failed` audit, including terminate events.
- **Fix:** Event-type-specific failure states and reconciliation; do not resurrect TERMINATED service as SUSPENDED.
- **Accept:** Repeated termination failure stays pending/manual review; never marked successful or suspended.

### NEW-338 · P1 · Order-level Stripe subscription duplicated per service
- **Location:** `src/modules/checkout/checkout.ts:198-229`, `src/modules/payments/webhooks.ts:375-462`
- **Proof:** One Stripe subscription for full multi-service order, but webhook inserts same PSP subscription ID and full order amount as renewal price for each local service; also hardcodes local billing interval MONTHLY.
- **Fix:** One PSP subscription entity linking per-service allocations, or real Stripe line items per service; retain interval and per-service billing amount.
- **Accept:** Order with 2 services has unambiguous cancellation/renewal, correct sum and billing interval.

## MFA and step-up policy

**Mandatory or strongly recommended:** staff console entry, changing ownership, issuing high privilege invites, credential/passkey lifecycle, PSP/refund/provider secrets, destructive admin service actions. Require **recent step-up** for ownership and PSP changes; avoid using email OTP alone for staff.

**No extra MFA prompt per click:** ordinary Start/Stop/Restart, console access, viewing usage, editing routine server files, support navigation. Keep permissions on backend, and confirmation for especially destructive restore/reinstall actions.

Existing guarded operations (such as staff refund, admin terminate and TOTP replacement) should remain guarded. New gaps must not be hidden by frontend-only button gating.

## Controlled-release gates

1. Stripe test mode: one-to-one settlement, refund, cancellation, renewal, retry/out-of-order.
2. Multi-tenant access: OWNER/TECH_ADMIN/BILLING/VIEWER/shared user tests.
3. Pterodactyl E2E with real panel; cPanel/Proxmox **disabled until their real adapters pass**.
4. Crash/outbox/provider state reconciliation and forced outage tests.
5. Real backup restore drill, SMTP delivery, admin alerting and edge TLS.
6. Petal UX role/provider/state matrix, route races, visual comparisons.
7. Small invite-only pilot with manual oversight and rollback plan.

**Scope:** Fortless is an operator-managed hosting business, not a hyperscale provider. Keep solution pragmatic and operationally reliable; do not rewrite the frontend or create speculative security features.
