# Visual implementation contract for Fortless

## Supplied sources, highest priority first
1. `references/design-system/out-original.html` and `panel-original.html`: raw owner-supplied visual/design system reference; inspect CSS, markup, tokens, responsive behaviour and component state examples.
2. `references/screenshots/current-fortless-hero.png` and `current-fortless-cta-footer.png`: current screen design and copy direction.
3. `references/design-system/fortless-landing-prototype.html`: earlier visual prototype and interactive pattern examples. Do not overwrite established later styling from screenshots based on this prototype.
4. `references/brand/fortless-original-logo-reference.png`: original FL mark, source of shape truth. Other brand patterns are art, not canonical vector assets.

## Verified visible color tokens from original source (check source for details)

Typography uses system/SF Pro Display/Inter Tight (weight 500–800), JetBrains Mono for technical snippets and badges.

## Required component implementation
- Design system bridge: token dictionary -> CSS variables/themes -> React primitives with precise states. Preserve styles for buttons, inputs, form validation, selectors, dialogs, badges, navigation, data tables, empty/skeleton/loading/error states and permission-denied states.
- Components must meet keyboard and accessible name/focus requirements (WCAG principles), including theme toggle and mobile nav.
- Use existing rounded pill CTA buttons, flat card surfaces and navy/blue/lime hierarchy. Avoid default shadcn/Tailwind generic styling unless component matches owner reference exactly.
- Responsive web, auth and app screens from narrow phones to wide desktops; no content under sticky bars, horizontal page overflow, small iPhone input zoom, clipped modals or unusable tables.
- Hero/CTA image on the right should be clipped by the lime card container and not overlap copy/button; on mobile it may reduce size, lower opacity, or move below text. Use alt="" for purely decorative pattern, respect reduced motion.
- Every app screen has correct auth state and backend model; demo content clearly marked. Do not hardcode user emails/names/service statuses as truth.

## Authentication layout
- Login / Register / Forgot / Reset / Verify pages share a consistent auth shell. Use design system inputs, validation states, pill buttons, subtle monochrome headings, optional right-side brand treatment using FL pattern, no heavy shadow/glass.
- Password fields need reveal toggle and show caps/requirements clearly. Error messages must be safe: don't leak user existence on recovery. Rate limits, CSRF/session security, MFA and email verification enforced by backend rather than UI alone.
- Remember design and accessibility: `autocomplete`, labels, focus, validation, proper loading, resend verification throttling, password manager compatibility.

## Dashboard/Admin layout
- Public header is distinct from authenticated app/sidebar and admin shell but they share primitive tokens and brand.
- Client app supports dashboard, My Services, individual Service, Billing/Invoices/Payments, Domains (later), Support, Account/Security, Notifications.
- Admin has separate guarded shell and routes for overview, users/accounts, catalog/plans, orders, invoices/payment reconciliation/refunds/disputes, services/provider nodes, tickets, audit events, product CMS, configuration, incident/operations tools.
- Never expose a functional-looking destructive or paid button with a fake action; disable it with clear explanation until actual backend exists.

## Brand work
For new artwork use the original mark and brand colors, not a near-shape generated by image tools. Generated patterns are presentation assets only and might not tile seamlessly; if CSS background-repeat is desired, recreate proper SVG/vector tile from the original logo with a seamless geometric layout.
